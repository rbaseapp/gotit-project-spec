# 44 — Multilingual concepts and shared study images

Date: 2026-10-16. Status: implemented locally in the Backend and Admin working trees; not deployed. This document owns the feature contract.

Current addition: automatic AI assignment and historical-word backfill are implemented locally. The **Automatic assignment** section below supersedes the earlier manual-only baseline.

## Outcome and scope

FR-CON-01: staff can associate expressions in any supported BCP-47 language with one reviewed lexical meaning. FR-CON-02: all uniquely matched expressions use one persistent image per application/concept/image revision, independent of language pair, learner and configured provider model. FR-CON-03: staff can manage meanings, translations and image lifecycle in Admin. Saving a concept does not create learning items, transfer mastery between languages or award evidence/XP.

`apple / תפוח / تفاحة / עפּל` can all identify the apple-fruit concept. Apple the company is a different meaning. Equivalence can be curated by staff or resolved by AI from the confirmed meaning; spelling and provider-generated keys alone do not prove equivalence. The automatic-assignment migration queues historical learner words for bounded backfill. The starter migration inserts the reviewed apple-fruit meaning in applications with existing product profiles, with English, Hebrew, Arabic, Yiddish, German, French, Spanish, Russian and Chinese expressions. New concepts can also be managed through Admin.

## Identity and resolution

The Backend owns three additive `product_gotit` tables in migration `1792191000000_multilingual-concepts.js`:

- `lexical_concepts`: application scope, immutable key, title, definition, visual description, optional reviewed English stock query, active/disabled status, optimistic revision and image revision. `is_seed` distinguishes untouched starter data for rollback protection.
- `concept_expressions`: application/concept foreign key, canonical exact language tag, display expression and capture-compatible NFKC/lowercase/whitespace-normalized lookup text. A concept requires at least two distinct languages; normalized duplicates within a language are rejected. Homonyms may belong to multiple concepts.
- `concept_image_assets`: one row per `(application_id, concept_id, image_revision)`, bounded binary data, provider/model/source attribution, generation claim token and expiry. Its composite foreign key preserves application boundaries.

Resolution intersects the concepts containing the exact source-language/expression and the exact translation-language/expression. Exactly one active result is required. Zero or multiple candidates retain the existing lexical-image path. No locale-base guessing or English pivot translation is performed. Existing learning item IDs, signed capture selections, semantic revisions, attempts and language-specific learning state are unchanged.

## Image lifecycle

Practice study images and catalog unit image GET/POST consult concepts before legacy per-item/per-pair images. A matched concept takes precedence over old lexical images. Read-only catalog GET returns its cached image or null and never calls a provider. A missing concept image can be created by the existing image provider in a learner request or explicitly through Admin. The curated visual description replaces incidental source context; private captured sentences are not shared or stored in the concept cache. An optional staff-approved English `stockSearchQuery` (up to 100 characters; stored as `stock_search_query`) retains the existing stock-first provider policy and tag relevance checks. Empty search skips stock lookup and uses illustration generation. The seeded apple has `apple fruit isolated`. Cached images remain available without any provider.

Image bytes and attribution are shared; alt text remains the requested source expression. Provider/model changes do not regenerate a concept image. Adding languages, renaming a concept or changing aliases keeps the image. Changing the definition/visual description/stock query or explicitly resetting it increments the image revision. Old media is retained but no longer used by current resolution. Disabling a concept prevents shared resolution and cached retrieval for it.

A persistent five-minute claim prevents simultaneous language pairs/processes from creating duplicate paid work. Generation occurs outside database transactions. A competing request returns cached data if ready, otherwise null; retry after the first request finishes. Failed generation releases its claim; a crashed worker's claim expires. Publication checks the current active image revision and claim token, preventing stale workers from publishing after a semantic edit. Practice also rechecks the learner item's revision before returning generated concept media. As with the existing providers, paid work interrupted after provider completion and before durable storage cannot guarantee exactly-once billing.

## Admin contracts and screen

SCR-ADM-CON: **מושגים ותמונות / Concepts** offers search by concept or expression, create/edit, multilingual expression rows, active/disabled selection, current image/attribution preview, image reset and quick explicit stock/AI replacement actions. The Hebrew guide explains ambiguity and when regeneration is necessary. The UI preserves the existing locked-editing notices and five-minute authenticator flow.

| GET | `/api/v1/admin/concepts/:id` | Scoped detail, expressions and current image or null |
| POST | `/api/v1/admin/concepts` | Strict operationId, reason, expectedRevision:null, resetImage, document |

The document contains key, title, definition, visualDescription, status and 2–200 `{languageCode,text}` expressions across at least two languages. Reads require independently verified administrator access. Every write/action requires Core-owned `content.write` and MFA, plus owner-side validation, optimistic conflicts, audit reason and persistent operation receipts. Audit resource is `concepts`; actions are `concept.save` and `concept.image.request`. Image requests are audited before external work, then complete outside the short command transaction. Retrying the same operation/payload ensures the same cached image. Changed payloads conflict; provider unavailability returns `CONCEPT_IMAGE_UNAVAILABLE`, never simulated success.

Admin's gateway has fixed concept resource paths and strict commands. Only concept, word and word-image detail responses allow up to 4.3 MB to accommodate the existing 3 MB binary limit encoded in JSON; all ordinary responses retain the 1 MiB bound. The generate action retains the existing explicit 120-second gateway deadline. No new browser credentials, direct DB access, Core changes, Web/Chrome request fields or learner API response fields are introduced.

Unlinked words can open concept creation with the source and primary translation prefilled, or search existing concepts. ## Automatic assignment - 2026-10-16

FR-CON-07: every saved learner word is durably queued for automatic meaning assignment. FR-CON-08: AI resolves inflections, optional vowel marks and ambiguous senses, reusing an existing active concept or creating a new one without asking the learner to classify it. FR-CON-09: saved historical words are queued for backfill. This supersedes the manual-only matching descriptions above; manual concept management remains supported.

Migration `1792192000000_automatic-concept-assignment.js` adds `concept_assignment_jobs` and `learning_item_concepts`, plus meaning revision, origin and canonical English lemma/part-of-speech metadata on concepts. Composite foreign keys bind jobs and assignments to the owning application/user/item and concepts to the application. A generated, indexed `search_text` strips optional Arabic/Hebrew vowel marks for candidate retrieval only. Exact stored expressions and normal capture identities are preserved; accents in other languages are preserved. Canonical lemma and English definition search indexes bound candidate lookup.

Database triggers enqueue jobs in the same transaction as learner-item inserts, semantic/language/part-of-speech changes, primary-translation changes, deletion and restoration. This covers manual/Chrome capture, imports, packs and administrator edits without duplicating each creation path. Capture receipts and signed selection provenance are unchanged. The existing save path wakes the worker after commit; a server timer also runs every ten seconds. Publication changes no learning evidence, mastery, review date or XP.

The worker first asks AI for a generic English lemma, precise lexical definition, part of speech, same-sense English search terms, source/translation dictionary forms and an isolated reusable visual description. The confirmed source/translation and up to 1,000 characters of saved sentence disambiguate meaning. The response is strict and bounded. It then retrieves up to forty active candidates using original and canonical forms, vowel-insensitive candidate lookup, English synonyms and definition search. AI selects one supplied candidate UUID or decides that none matches. A returned UUID outside the supplied application-scoped candidate list is rejected. No spelling-only or vowel-stripping-only merge is performed, and provider keys alone are never sufficient evidence to merge a meaning. Model retrieval/semantic quality is heuristic; semantically equivalent concepts outside the bounded candidate recall can still require later reconciliation.

If no candidate matches, a new active concept is created with origin=ai. Publication adds the actual captured forms and AI-resolved dictionary forms (maximum 200 expressions per concept; oversized raw expressions rely on the per-item binding), then records a versioned learner-item assignment with model provenance and matched/created decision. Raw captured sentences, page metadata and incidental private entities are not copied into shared concepts or assignment descriptors. Context is sent only to the existing server-side OpenAI provider, with store=false and untrusted-data separation. The model's generic lexical output is stored in the durable job for retry; input sentence text is read from existing scoped occurrences and is not duplicated in the queue.

Network calls run outside database transactions. A two-minute persisted claim prevents simultaneous workers from resolving the same job twice. Each call has a twenty-second provider deadline and a bounded response reader. A short application-level publication lock and candidate-snapshot recheck prevent concurrent first words in different languages from creating duplicate concepts against a stale candidate set. Up to three catalog re-decisions reuse the saved descriptor. Publication checks the claim token, job generation and current learner revision, preventing an in-flight old decision from linking an edited/deleted item. Semantic concept edits advance a separate meaning revision and requeue affected bindings; image-only changes keep bindings valid.

Transient/provider failures remain pending with safe error codes and exponential retry (30 seconds up to one hour); authentication/configuration/billing failures wait an hour instead of retrying on every tick. Daily-quota exhaustion uses the server-provided retryAfter window (up to 24 hours). A successful replay does not call AI again or requeue the word. A crashed worker's expired claim is recoverable. New and edited words have priority over migration backfill, and the next job is reselected after each decision. Work is bounded per cycle and stops accepting jobs during graceful shutdown. Failed external calls before durable response storage may still incur another paid call; exactly-once external billing is not claimed.

Practice and installed-catalog image reads use the current per-item meaning binding before legacy exact-pair resolution. While automatic classification is pending and AI is configured, media reads return image:null without generating a redundant per-language image. A completed binding shares the existing concept image even if the primary translation has a different tense/optional marks or the concept has multiple lexical candidates. Unbound catalog entries retain the existing exact-pair behavior. Learner request/receipt/media shapes remain backward compatible.

Admin word list/detail now exposes `conceptAssignmentStatus` (pending/processing/completed), a sanitized `conceptAssignmentError`, and the effective concept ID. The word's real owner scope is used for its image binding even when an administrator reads it. The Hebrew UI shows waiting/checking/retry state and refreshes active list/detail queries every ten seconds. Concepts expose origin and meaningRevision; all existing staff permissions, MFA and guarded management writes remain in force. No new mutation endpoint or browser-side AI credentials are introduced.

Configuration: the existing `OPENAI_API_KEY` enables the worker. Optional `OPENAI_CONCEPT_MODEL` overrides `OPENAI_TRANSLATION_MODEL`, then `OPENAI_PRIVATE_LESSON_MODEL` as fallback. Requests use adminAiFetch's trusted per-job runtime context so actual provider usage is attributed to the owning application/user; operation=concept-assignment. A separate server-side concept_assignment limit allows 200 AI calls per user per 24-hour limiter window and does not spend translation/image quotas. Without provider configuration, words stay durably pending; the service never invents semantic success. Existing legacy media remains available when automatic AI is not configured.

The generated expression column/index may rewrite/lock the existing expression table; assess size and rehearse on the intended dataset before a live rollout. Historical-word backfill is queued by migration and processes under the same bounded quota/cost controls. The down migration refuses rollback after resolved/attempted work; application rollback should retain the additive schema and queue. No live DB change, deployment or paid provider call was made during implementation.
